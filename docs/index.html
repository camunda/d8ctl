Technical Preview · Agent CLI for Camunda

d8ctl — say Droid-8-c-t-l

One CLI. Every Camunda API. Built for agents.

Give every agent one way to operate Camunda — the Orchestration Cluster, Console, and Hub — without a new integration for each API, and without breaking when a customer is still on last year’s cluster.

  • One tool, not a toolkit. Agents stop choosing among N CLIs with N dialects.
  • They learn by asking. --help is the contract. No prompt pack to maintain.
  • Every estate works. The surface matches the version in front of them — older or newer.
$ d8ctl --help
  cluster    Orchestration Cluster
  console    Camunda Console
  hub        Camunda Hub

$ d8ctl cluster process-instances search --filter='{"state":"ACTIVE"}'
$ d8ctl console clusters list
$ d8ctl hub connectors search --name='*slack*'

One surface for the whole product.

Customers do not buy “the REST API.” They buy Camunda. An agent that can start a process, list SaaS clusters, and find a Hub connector — in one grammar — is an agent that can do the job. Shipping a new product surface should not mean shipping a new agent tool.

Orchestration Cluster is live today. Console and Hub plug in as more catalogs behind the same parse, help, and dispatch. Adding an API is a generator input, not a new CLI programme.

Spike: namespace cluster only. The parser already keys on namespace; the next catalogs sit beside it.

Agents discover. You don’t document a prompt.

Every agent runtime already knows how to run a command and read stdout. Progressive --help is the schema: what exists, what it needs, what it does. No MCP server to host, no tool catalog to republish when the API moves.

Root → product → resource → flags. The agent walks in as deep as the task requires. Humans get the same path. Both cluster jobs activate and cluster activate jobs work — noun-verb or verb-noun.

One binary. Every supported version.

Support does not fork the CLI per release train. Point the same binary at an 8.6 cluster and at 8.11: the agent only sees what that cluster can do. No “upgrade the agent’s tools” ticket when a customer has not upgraded the broker.

The OpenAPI spec already marks when each operation landed (x-added-in-version). d8ctl asks the cluster who it is, and hides everything newer. Fields can carry the same mark, so an old cluster keeps the command and loses only the new flag.

8.6create / cancel / activate
8.7+ resources
8.8+ search
8.9+ statistics
8.11full catalog
$ # same binary, two customers
$ d8ctl cluster --help          # 8.6 estate  → 91 operations
$ d8ctl cluster --help          # 8.11 estate → 247 operations
$ d8ctl cluster jobs search     # 8.6: unknown (added in 8.8)

Spike offers the full catalog. The version field is already on every command; filtering on it is the next cut.

Nobody hand-writes this CLI.

Every command materialises from the API specification — deterministically, the same way every time. That is only possible because Camunda treats the spec as a product: version markers on every operation and field, contract-tested against the real engine. No engineers wrapping endpoints. No agents burning tokens to guess an implementation. Spec in, CLI out — and at runtime, from a live cluster’s spec.

A generator turns the spec into a table; one small engine handles parsing, help, and HTTP for all 247 operations. Zero per-operation code, so coverage cannot drift. A new endpoint is a regenerate, not a project — and when the cluster publishes its spec, not even that: new operations appear as catalog rows in the binary already installed.

The spec is a guarantee, not documentation: the API does what the spec says it does. That is enforced in CI, not by convention.

  • Linted. Spectral rules — structure, required permissions, semantic key types, consistency annotations, naming — gate every spec change, and the custom rules have their own tests.
  • Versioned. Every operation and field must carry a correct version marker.
  • Contract-tested. api-test-generator derives tests from the spec itself, for Orchestration Cluster and Hub.
  • Proven on every line. Nightly API suites run against each supported version, 8.7 through main.

c8ctl for humans. d8ctl for agents.

People keep the rich CLI they already have. Agents get something they can call on every step without dragging a runtime into the sandbox — one file, no install story, cheap enough to fan out.

c8ctl stays the human product: profiles, plugins, deploy, pretty search. d8ctl is a 2 MiB native binary. Drop it on a laptop, a CI runner, or an agent jail. It runs. Help returns in milliseconds, not after a Node boot.

Why D? Lighter than Node. Cheaper to build than Rust.

An agent calls its tools on every step, so every call has to be instant and the tool has to drop into any sandbox. And the code behind it has to be cheap to change — by engineers and by agents. D is the one choice that gives us both: a tiny native binary at light speed, with Rust-class safety and none of Rust’s build bill.

vs Node (c8ctl)

No JavaScript runtime to boot, no node_modules, no install step. One 2 MiB file that just works everywhere. It answers in about 9 ms using 7 MiB of memory; the same call through Node takes about 160 ms and 108 MiB. Live API calls cost only a few milliseconds more than raw curl. Fan out twenty calls and you feel it.

vs Rust

As our Rust investment grew, we started paying in velocity: build time, CPU, and disk caches, paid by every engineer and every agent working on the code. D gives the same native runtime and the same class of compile-time memory safety, from one compiler download, building in seconds, with no gigabyte target/ caches on every laptop, runner, and sandbox.
