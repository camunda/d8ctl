Agent CLI for API.

d8ctl is a projection, not a product surface. The OpenAPI spec is the command tree. There is no hand-written handler per operation. An agent that can type --help can operate the whole cluster.

Zero-touch projection

A generator reads the D SDK’s bundled spec-metadata and writes a static table. Parse, help, and dispatch walk that table. If the API grows an operation, regenerate — it is a command. No per-op switch, no YAML command defs, no “we forgot to wrap searchJobs.”

What is generated

  • 244 rows: method, path, verb, resource, summary
  • Path params as positionals, in spec order
  • Query params as --name=value
  • 336 top-level body fields as documented flags

What is not

  • The HTTP client (D SDK + libcurl)
  • Auth, retry, backpressure (CAMUNDA_*)
  • The argv parser and progressive help
  • One invoke() that calls requestJson
$ make generate
generate: 244 commands, 121 with body flags (336 fields)

$ d8ctl cluster jobs activate --help   # flags came from JobActivationRequest
$ d8ctl cluster process-instances search --filter='{"state":"ACTIVE"}'

Multipart (deploy, documents) is refused until file flags exist. Union bodies (create process instance) stay --body='{…}' — there is no honest single shape to flatten.

Progressive help is MCP, in depth

An MCP server is a catalog plus tool schemas plus a way to call them. A well-factored CLI is the same object, already on PATH, already streamable, already something every agent runtime knows how to invoke. d8ctl treats --help as the schema endpoint.

  1. Root — there is one namespace: cluster. The agent does not guess product names.
  2. Resource list — d8ctl cluster --help is the tool index. 166 resources, verbs beside each.
  3. Verb — d8ctl cluster jobs --help is activate and search, with HTTP method and path.
  4. Flags — d8ctl cluster jobs activate --help is the JSON Schema: required starred, types hinted, first sentence of the OpenAPI description. Nested objects stay JSON strings. 
$ d8ctl cluster jobs activate --help
d8ctl cluster jobs activate

Activate jobs
  HTTP        POST /jobs/activation
  operation   activateJobs
  added in    8.6
  body        flags below, or --body='{…}' (wins on conflict)

Body flags (top-level JSON fields):
 * --type=VALUE              The job type, as defined in the BPMN process
   --worker=VALUE            The name of the worker activating the jobs
 * --timeout=INT             Lease timeout in ms
 * --maxJobsToActivate=INT   The maximum jobs to activate
   --fetchVariable=JSON      Variables to fetch; empty means all
   --requestTimeout=INT      Long-poll timeout
   --withLease=true|false    Activate with a lease
  * required unless supplied via --body.

Both orders parse: cluster jobs activate and cluster activate jobs. --order only changes how help lists them. An agent that learned kubectl’s noun-verb and one that learned git’s verb-noun both land on the same operation.

API Time Machine

One binary carries the newest catalog. The command tree the agent sees is the catalog cut to the server it is talking to. Point d8ctl at 8.6 and searchJobs is not a command. Point it at 8.8 and it is. No “upgrade the CLI” step. No d8ctl@8.6 on PATH. The API version is the CLI surface.

The cluster already knows what it is. We read that — a response header, or GET /topology — and drop every operation whose added in is newer than that version. Help, completion, and dispatch all walk the filtered table. An agent that only ever types --help cannot invent a flag the broker will 404.

8.7 + resources, documents

$ CAMUNDA_REST_ADDRESS=https://old.example \
    d8ctl cluster jobs search --help
d8ctl: unknown command 'jobs search' on API 8.6 (added in 8.8).
       Talking to 8.6. See `d8ctl cluster jobs --help`.

Discovery is the handshake. First call (or first --help that needs the live tree) asks the cluster who it is. After that, every progressive-help screen is already in the past of that cluster. The agent plans against what exists, not against what we shipped last Tuesday.

Spike today: the catalog is compiled in and every row is offered. Time Machine is the next cut — version from GET /topology (or a negotiated header), then filter on added in. The field is already on every command.

Why D

Agents pay process startup on every tool call. A Node CLI that does the same job here boots in ~160 ms and 110 MiB just to print --version. d8ctl is 9 ms and 7 MiB. Live calls sit 3–8 ms above curl. That is the tax you want when a planner fans out twenty searches.

Native, not “compiled JS”

LDC, Phobos statically linked, system libcurl. No GC warmup, no module graph, no plugin discovery. The catalog is 76 KiB of static data in the binary.

The same @safe ratchet as the SDK

Every module @safe:. DIP1000, nosharedaccess, bounds checks on in release. Two @trusted wrappers for stdout/stderr. Zero extra dub packages.

In action

# both orders are the same command
$ d8ctl cluster topology get
$ d8ctl cluster get topology

# flags from the spec, not a hand-written parser
$ d8ctl cluster jobs activate \
    --type=probe:never --timeout=1000 --maxJobsToActivate=1

# search: empty body is {}, or pass a filter
$ d8ctl cluster process-instances search --page='{"limit":1}'
$ d8ctl cluster process-instances search \
    --filter='{"state":"ACTIVE"}' --page='{"limit":5}'

# path params are positional; --body still wins on conflict
$ d8ctl cluster process-instance cancel 38197 --operationReference=1
$ d8ctl cluster process-instance create --body='{"processDefinitionId":"order"}'

# see the wire without hitting it
$ d8ctl cluster jobs activate --type=x --timeout=1 --maxJobsToActivate=1 --dry-run
dry-run POST /jobs/activation
{
    "maxJobsToActivate": 1,
    "timeout": 1,
    "type": "x"
}
